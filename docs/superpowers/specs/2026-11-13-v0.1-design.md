# hwp-parse-bench v0.1 설계

작성 2026-11-13. 사용자 부재 중 ai-oss-main과 ai-oss-support가 함께 정했다. 사용자가 정한 것은 "RAG 개발자 대상", "HWP 파싱 벤치마크로 방향 전환", "형식은 HWP·HWPX만" 세 가지다. 나머지 결정은 각 절의 **결정** 줄에 이유와 함께 적는다.

## 1. 왜 만드는가

- HWP·HWPX를 Markdown으로 바꾸는 RAG용 도구는 이미 여럿 있다(kordoc, unhwp, python-hwpx, rhwp-python, hwp-hwpx-parser, hwpforge 등).
- 그런데 이 파일들을 그대로 입력으로 받는 공개·재현 가능한 벤치마크는 없다(2026-11-13 조사, 근거는 부록 A).
  - kordoc 자체 벤치: 문서 묶음이 비공개이고 고정돼 있지 않다.
  - KoOCR-Bench: 쪽 이미지를 입력으로 받는 OCR 벤치다.
  - unhwp README도 "We know of no public benchmark for HWP/HWPX documents yet"라고 적고 있다.
- 그래서 RAG 개발자가 "어느 HWP 파서를 써야 하나"를 수치로 판단할 근거가 없다. 이 벤치는 그 근거를 만든다.

## 2. 범위

v0.1에 넣는 것:
- **입력:** HWP 5.x, HWPX 파일 그대로. 네이티브 파서만 다룬다.
- **코퍼스:** 재배포할 수 있는 공공 문서 40~60개를 저장소에 직접 넣고, 해시와 버전을 고정한다.
- **정답:** HWPX 원본 XML에서 독립 참조 추출기로 만든다. 정답마다 검수 상태를 표시한다.
- **지표:** 본문 텍스트 유사도, 표 구조와 내용(TEDS / TEDS-S), 제목 계층 F1, 실패율, 처리 시간.
- **어댑터:** 키 없이 돌릴 수 있는 공개 파서 9종. 버전을 고정하고, 어댑터마다 격리된 환경에서 실행한다.
- **결과:** JSON 결과, 자동 생성되는 순위표(README), 한 줄 재현 명령.

v0.1에 넣지 않는 것:
- **OCR·PDF 입력:** KoOCR-Bench와 KDoc-OCRBench가 이미 다룬다.
- **RAG 하류 지표:** 질문-정답 쌍으로 재는 검색 적중률, 청크 메타데이터 정확도. v0.2로 미룬다.
- **상용 API를 순위표에 넣는 것:** 선택 어댑터로만 둔다.
- **LibreOffice+H2Orestart:** v0.2로 미룬다.

**결정:** v0.1은 "구조 충실도" 벤치로 한정한다. 한 달 안에 정답 품질을 지킬 수 있는 범위가 여기까지다. RAG 하류 지표는 정답 문서 모델이 안정된 뒤에 얹는 편이 맞다.

## 3. 저장소 구조

```
hwp-parse-bench/
  corpus/
    manifest.jsonl        # 문서마다 한 줄: id, 파일, sha256, 출처, 라이선스, 형식, 영역 태그, 짝 문서
    files/<id>.<hwp|hwpx>
  truth/<id>.json         # 정답 문서 모델 (status: auto | reviewed)
  src/hwpbench/
    model.py              # 공통 문서 모델 (Block, Table, Cell)
    reference/            # 독립 참조 추출기 (HWPX XML → 문서 모델). 비교 대상 파서의 코드를 쓰지 않는다
    normalize/            # 파서 출력(Markdown, GFM, HTML 표) → 문서 모델
    metrics/              # nid, teds, headings
    adapters/             # 파서별 실행 스크립트와 고정 버전
    runner.py             # 어댑터를 격리 프로세스로 실행하고, 타임아웃과 실패를 기록
    report.py             # 집계와 순위표 생성
    cli.py                # hwpbench run | score | report | truth | review
  results/<run-id>/       # 원 출력(md), 점수 json, 환경 정보
  tests/
```

## 4. 공통 문서 모델

- `Document = list[Block]`
- `Block`은 다음 다섯 가지 중 하나다.
  - `Heading(level, text)`
  - `Paragraph(text)`
  - `ListItem(level, text)`
  - `Table(rows: list[list[Cell]])`
  - `Footnote(text)`
- `Cell`은 `text`, `rowspan`, `colspan`을 가진다. 병합 셀은 좌상단 칸에만 둔다. 격자는 HTML 표와 같은 방식으로 표현한다.
- 텍스트 정규화는 정답 쪽과 파서 쪽에 똑같이 적용한다.
  - NFC 정규화
  - 연속 공백을 하나로 접기
  - 전각과 반각 공백 통일
  - 제로폭 문자 제거
  - Markdown 강조 기호 제거
  - 전화번호·전자우편 가림 (`000-0000-0000`, `x@x`)

## 5. 코퍼스

- **출처:**
  - 국가법령정보센터의 법령 별표·서식. 저작권법 제7조에 따라 보호받는 저작물이 아니다.
  - 공공누리 제1유형(출처표시) 공공기관 문서.
  - 제3·4유형(변경금지)은 정답을 만드는 일과 충돌할 수 있어 제외한다.
- **manifest 필드:**
  - `id`, `file`, `format`
  - `sha256`
  - `source_url`, `download_url`, `retrieved_at`
  - `license`(`kr-copyright-art7` 또는 `kogl-type1`)
  - `attribution`
  - `tags`
  - `pair`: 같은 문서의 HWP↔HWPX 짝
- **영역 태그:** `general`, `table-heavy`, `nested-table`, `merged-cells`, `footnote`, `textbox`, `multi-column`, `equation`, `distribution`(배포용), `encrypted`, `hwp3`
- **결정:** 파일을 저장소에 직접 넣는다. kordoc 벤치는 수집 스크립트만 공개해서 같은 코퍼스를 다시 만들 수 없다. 우리는 데이터를 직접 내고 버전을 매긴다. 크기가 커지면 v0.2에서 Hugging Face 데이터셋으로 옮긴다.

## 6. 정답

- **참조 추출기:** HWPX(zip, OWPML XML)의 `Contents/section*.xml`을 직접 읽어 문서 모델을 만든다.
  - 대상 요소: 문단(`hp:p`), 표(`hp:tbl`, `hp:tc`의 `cellSpan`), 각주, 글상자 안 문단
  - 제목은 개요 수준(`outline`) 문단 모양과 스타일 이름("개요 n", "제목")으로 판단한다.
- **독립성:** 비교 대상 파서의 코드는 import하지도 복사하지도 않는다. lxml과 표준 라이브러리만 쓴다.
- **HWP 문서:** 같은 출처에서 HWPX 짝을 받을 수 있으면 그 정답을 함께 쓴다. 짝이 없는 HWP는 `text-only` 영역으로 두고, 본문 텍스트 재현율만 잰다. 이때 정답 텍스트는 PDF 짝에서 뽑는다. PDF도 없으면 v0.1에서는 넣지 않는다.
- **검수:** `hwpbench review <id>`로 원본 렌더(PDF 짝이 있으면 PDF)와 정답 Markdown을 나란히 보는 HTML을 만든다. 사람이 고친 정답은 `status: reviewed`로 표시한다. 순위표는 전체 점수와 reviewed만으로 낸 점수를 모두 보여 준다.
- **결정:** v0.1 출시 조건은 표가 많은 문서의 정답을 최소 10개 검수하는 것이다. 사용자 검수가 필요하다. → **사용자 결정(2026-11-13):** 검수는 나중에 하고 `auto` 정답으로 먼저 공개한다. README에 검수 전임을 밝힌다.

## 7. 정규화 (파서 출력 → 모델)

- 파서는 Markdown(GFM 표)을 내기도 하고, Markdown 안에 HTML 표를 섞어 내기도 한다(kordoc 기본값).
- markdown-it-py로 블록을 나누고, 그 안의 HTML 표는 lxml.html로 격자로 바꾼다. 표 셀의 `rowspan`과 `colspan`도 읽는다.
- 일반 텍스트만 내는 파서(gethwp, pyhwp txt 등)는 문단 목록으로만 해석한다. 그래서 표와 제목 점수는 0이 아니라 "지원 안 함"으로 표시한다.

## 8. 지표

- **텍스트 NID:**
  - 표 밖 본문 텍스트를 블록 순서대로 이어 붙여 비교한다.
  - 값은 1 − 편집거리 / max(len)이다.
  - rapidfuzz의 Levenshtein을 쓴다. 정답과 출력의 순서가 크게 다른 경우도 이 값에 반영된다.
- **표 TEDS:**
  - 문서 안의 표를 정답 표와 짝지은 뒤 평균을 낸다. 짝짓기는 헝가리안 매칭으로 하고, 비용은 1 − TEDS다.
  - 짝을 못 찾은 표는 0점이다.
  - TEDS-S는 셀 텍스트를 무시하고 구조만 본다.
  - 구현은 APTED(MIT) 기반으로 직접 작성한다. PubTabNet 원본 구현의 라이선스는 확인이 필요하다.
- **제목 F1:** (level, 정규화 텍스트) 쌍이 정확히 맞으면 맞힌 것으로 센다. 레벨을 무시한 F1도 따로 낸다.
- **운영 지표:** 실패율(예외, 타임아웃 60초, 빈 출력), 문서당 처리 시간 중앙값.
- **집계:** 전체 점수, 형식별 점수(HWP/HWPX), 영역 태그별 점수를 낸다.

## 9. 어댑터와 실행

- 어댑터마다 하나의 파일에 고정 버전과 실행 함수를 둔다.
- 실행은 별도 프로세스로 한다.
  - Python 파서: `uv run --isolated --no-project --with <pkg>==<ver> python -m hwpbench.adapters.<name> <in> <out>`
  - kordoc: `npx -y kordoc@<ver>`. 지원하는 Markdown 출력 옵션을 쓰고, 기본 출력과 GFM 출력을 둘 다 잰다.
- 격리하는 이유:
  - 파서끼리 의존성이 충돌하지 않게 한다.
  - 파서가 죽거나 멈춰도 벤치는 계속 돈다.
  - 버전이 결과 JSON에 그대로 남는다.
- **v0.1 대상:**
  - kordoc (npm)
  - unhwp, python-hwpx, hwp-hwpx-parser, hwpforge, rhwp-python, gethwp, llama-index-readers-hwp (PyPI)
  - pyhwp: AGPL이라 별도 프로세스로만 호출하고 코드는 넣지 않는다.
- **선택 어댑터(키가 있을 때만):** Upstage Document Parse, LlamaParse. 순위표에는 따로 표시한다.
- 문서마다 원 출력(md)을 `results/`에 남겨, 점수가 어떻게 나왔는지 누구나 다시 볼 수 있게 한다.

## 10. 보안·법

- 입력 파일은 신뢰하지 않는다. 파서는 별도 프로세스에서 타임아웃을 걸고 실행한다. 우리 참조 추출기는 zip 폭탄을 막기 위해 압축 해제 크기를 제한하고, XML은 외부 엔티티를 끈 상태(`resolve_entities=False`, `no_network=True`)로 파싱한다.
- README에 다음을 적는다.
  - 한컴 공개 문서 참고 문구: "본 제품은 한글과컴퓨터의 한/글 문서 파일(.hwp) 공개 문서를 참고하여 개발하였습니다."
  - 상표 고지: 한글·한컴·HWP·HWPX는 한컴의 등록상표이며, 이 프로젝트는 한컴과 제휴 관계가 없다.
  - 공공누리 출처 표시
- 코드 라이선스는 MIT, 코퍼스는 각 문서의 원래 라이선스를 따른다(manifest에 기록). 정답·주석은 CC-BY-4.0으로 한다.

## 11. 테스트

- 참조 추출기는 작은 합성 HWPX(직접 만든 XML zip)로 단위 테스트한다. 병합 셀, 중첩 표, 각주, 제목 수준을 다룬다.
- 정규화는 GFM 표, HTML 표, rowspan·colspan, 이스케이프된 `|`를 단위 테스트한다.
- 지표는 손으로 계산한 작은 예로 고정한다. 같은 표는 TEDS 1이고, 셀 하나가 다르면 기대값이 나와야 한다.
- 실행기는 가짜 어댑터로 시험한다. 성공, 예외, 타임아웃, 빈 출력을 모두 다룬다.
- CI는 단위 테스트와 lint만 돌린다. 전체 벤치는 무겁고 외부 패키지가 필요해서 수동으로 실행한다.

## 12. 열린 문제 (사용자 확인 필요)

- 저장소 이름과 공개 시점. 공개 전에 kordoc·KoOCR 쪽과 겹치는지 확인할 것을 권한다.
- 정답 검수 10개 이상은 사용자 시간이 필요하다.

## 부록 A. 선행 조사 요약 (2026-11-13, ai-oss-support)

- **kordoc bench:** 방법론이 가장 비슷하다(HWPX 원본을 정답으로 쓰고 칸 F1을 잰다). 다만 코퍼스가 비공개이고 비교 대상이 하나뿐이다.
- **KoOCR-Bench:** HWPX 표를 정답으로 쓰지만 입력이 이미지다.
- **opendataloader-bench, dp-bench, OmniDocBench:** PDF만 다룬다.
- **arXiv·KCI·AI Hub·대회:** HWP 파일을 입력으로 받는 파싱 벤치는 없었다.

## 부록 B. 구현하면서 바뀐 점 (2026-11-13 새벽, ai-oss-support 검토 반영)

- **코퍼스 실측:**
  - 법제처의 "HWPX 내려받기"는 HWP와 바이트가 같다(34건 확인). 그래서 법령 별표는 HWP 전용이고, 한컴 PDF를 약한 정답으로 하는 **텍스트 트랙**(순서 무관 글자 F1)으로 돌렸다.
  - HWP↔HWPX 짝은 정책브리핑에서만 나왔다. 본문 유사도 0.98 이상만 인정한다(7건). 0.27인 "짝"도 있었다.
- **정책브리핑 라이선스:** "텍스트에 한하여" 공공누리 1유형이다. 첨부에 사진·로고와 담당자 실명·전화번호가 있다. 기본값은 저장소에 넣지 않고 `hwpbench fetch`(URL + SHA-256)로 받는 것이다. 정답(`truth/`)에는 텍스트만 들어간다. **사용자 결정(2026-11-13):** 동봉하지 않고 해시로 받는다. 담당자 전화번호·전자우편은 정답과 파서 출력 모두에서 같은 규칙으로 가린다(추출기 버전 4). 이름은 그대로 둔다.
- **지표:**
  - NID는 opendataloader-bench 정의(Indel)를 쓴다.
  - 주 표 지표는 **TEDS 격자(2행 2열 이상)**다. 보도자료 제목 상자 같은 1행 꾸밈 틀을 kordoc·unhwp는 의도적으로 글로 편다. 모든 표 기준으로는 이것이 "표 누락"이 되어 RAG 관점의 품질과 어긋난다.
  - "모든 표" 기준과 "병합 없는 격자 표"(GFM 출력의 공정 비교) 기준은 보조 열로 둔다.
  - 제목 F1은 v0.1 정답에 개요 스타일 제목이 없어 순위표에서 뺐다.
- **TEDS 구현:** PubTabNet 구현은 GPL 의존성(`distance`)이 있어 쓰지 않았다. apted(MIT)와 rapidfuzz(MIT)로 같은 정의를 직접 구현했다.
- **어댑터:**
  - ai-oss-support가 작성했다. PEP 723 고정 버전과 `uv lock --script`를 쓰고, kordoc는 npm lockfile을 쓴다.
  - 버전은 7일 규칙에 따라 최신판이 아닐 수 있다(kordoc 4.24.47, unhwp 0.23.1, python-hwpx 6.11.0, hwpforge 0.19.1).
  - 측정 실행은 macOS `sandbox-exec`(deny network)와 `UV_OFFLINE=1`로 돌린다.
- **채점 버그 수정 (첫 실행 후):**
  - 텍스트 트랙이 Markdown·HTML 기호까지 글자로 세던 것을 문서 모델을 거치도록 고쳤다.
  - markdown-it이 머리 행보다 칸이 많은 파이프 표의 남는 칸을 버리던 것을 줄 단위 직접 파싱으로 고쳤다.
  - 참조 추출기가 표 안 표의 문단을 공백 없이 붙이던 것을 고쳤다(추출기 버전 2).
